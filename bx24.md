## Executive Summary (Resumen Ejecutivo)

El componente `panel.propietario` ha evolucionado desde un componente Bitrix tradicional hacia un sistema complejo que orquesta un flujo BPMN completo de Postventa inmobiliaria (aprobaciones, validación de stock, agendamiento de técnicos todistas, cierre de tareas con evidencias y actas de conformidad).

La arquitectura actual presenta **grandes aciertos de diseño** (adopción de HighloadBlocks D7, desacoplamiento en servicios bajo `lib/`, consumo de API REST Spring Boot, notificaciones Bitrix UI nativas). Sin embargo, al evaluarlo bajo estándares de **Nivel Senior y Producción Empresarial**, se identifican **deudas técnicas críticas** en transaccionalidad, seguridad de endpoints AJAX, concurrencia, uso residual de IBlocks legacy y violación del Principio de Responsabilidad Única (SRP) en clases de servicio sobredimensionadas.

## 1. Principios SOLID y Clean Code

### A. Single Responsibility Principle (SRP) — Principio de Responsabilidad Única
* **Diagnóstico:** ⚠️ **Violación en servicios principales.**
* **Evidencia en código:**
  * [`RequerimientoHlService.php`](file:///home/bitrix/www/local/components/vita-panel-propietario/panel.propietario/lib/Services/RequerimientoHlService.php) supera las **1,720 líneas de código**. Esta clase actualmente centraliza:
    1. CRUD y gestión de requerimientos (Cabecera).
    2. Manipulación de stock de almacén e ítems de compra.
    3. Resolución y registro de aprobaciones técnicas.
    4. Carga y asociación de cotizaciones de compras.
    5. Negociación y propuestas de fechas con el cliente (Planes de trabajo).
    6. Catálogo y disponibilidad de todistas.
    7. Agendamiento de bloques de horario y asignación de tareas en Bitrix Tasks.
    8. Cierre de trabajo, validación y almacenamiento de evidencias fotográficas.
    9. Registro, upsert y consulta de Actas de Conformidad.
* **Impacto:** Cualquier cambio en la lógica de agendamiento o actas puede introducir regresiones en la gestión de almacén o presupuestos. Dificulta los tests unitarios.
* **Solución Senior:** Dividir `RequerimientoHlService` en servicios de dominio acotados:
  * `IncidenciaCabeceraService`
  * `MaterialStockService`
  * `PlanTrabajoService`
  * `TodistaAgendaService`
  * `ActaConformidadService`

### B. Open/Closed Principle (OCP) — Abierto para extensión, cerrado para modificación
* **Diagnóstico:** ⚠️ **Violación en la resolución de acciones y estados.**
* **Evidencia en código:**
  * En [`GridColumnBuilder.php`](file:///home/bitrix/www/local/components/vita-panel-propietario/panel.propietario/lib/Grid/GridColumnBuilder.php#L320-L442), la determinación de botones y acciones del Grid se realiza mediante una cadena monolítica de `if ... elseif` anidados evaluando cadenas mágicas (`$estadoServicio === 'AGENDAR_TRABAJO'`, `'TRABAJO_REALIZADO'`, etc.).
* **Solución Senior:** Implementar el **Patrón State o Action Strategy**:
  ```php
  interface GridActionProviderInterface {
      public function supports(string $estadoServicio): bool;
      public function getActions(array $row): array;
  }
  ```

### C. Liskov Substitution Principle (LSP) & Interface Segregation (ISP)
* **Diagnóstico:** ⚠️ **Ausencia de Interfaces en la capa de Servicios.**
* **Evidencia:** Los servicios (`RequerimientoHlService`, `SolicitudPedidoService`, `UserPermissionService`) son clases concretas sin contratos de interfaz. Los controladores dependen directamente de las implementaciones.
* **Solución Senior:** Definir interfaces para los repositorios y servicios externos (ej. `ApiClientInterface`, `RequerimientoRepositoryInterface`).

### D. Dependency Inversion Principle (DIP)
* **Diagnóstico:** ⚠️ **Instanciación directa acoplada.**
* **Evidencia en código:**
  * En [`class.php`](file:///home/bitrix/www/local/components/vita-panel-propietario/panel.propietario/class.php#L108-L115), el método `initDependencies()` y las acciones instancian directamente con `new RequerimientoHlService()`, `new SpringApiClient()`.
  * En [`SolicitudPedidoService.php`](file:///home/bitrix/www/local/components/vita-panel-propietario/panel.propietario/lib/Services/SolicitudPedidoService.php#L121), se ejecuta `new RequerimientoHlService()` dentro del método de procesamiento.
* **Solución Senior:** Inyectar dependencias en el constructor o utilizar un Service Locator / contenedor PSR-11.

## 2. Arquitectura y Separación de Responsabilidades

### Aciertos de la Arquitectura Actual
1. **Estructura Modular bajo `lib/`:** Cumple con la convención PSR-4 de Bitrix D7, permitiendo el autocargado limpio sin necesidad de `require_once` manuales dispersos.
2. **Separación de Lógica de Grid:** La creación de columnas y filtros se extrajo a `GridColumnBuilder` y `GridFilterBuilder`, aligerando el `class.php`.
3. **Controlador Centralizado:** `VitaPanelPropietarioComponent` implementa `Controllerable`, permitiendo que el frontend interactúe mediante la API AJAX nativa `BX.ajax.runComponentAction`.

### Brechas y Anti-Patrones Identificados
1. **Lógica de Base de Datos dentro de Vistas / Sliders:**
   * En [`slider-formato-pedido.php`](file:///home/bitrix/www/local/components/vita-panel-propietario/panel.propietario/templates/.default/slider-formato-pedido.php) y [`imprimir-acta-conformidad.php`](file:///home/bitrix/www/local/components/vita-panel-propietario/panel.propietario/templates/.default/imprimir-acta-conformidad.php), la vista ejecuta directamente queries SQL, consultas ORM `HL::getList()` y procesamiento de `$_REQUEST`.
   * **Corrección:** La plantilla debe recibir un **ViewModel** completamente procesado por el componente o invocar un endpoint que retorne los datos listos para renderizado.
2. **Contaminación del Ámbito Global en JavaScript:**
   * En [`costos.js`](file:///home/bitrix/www/local/components/vita-panel-propietario/panel.propietario/templates/.default/js/subprocesos/costos.js), funciones como `abrirModalActaConformidadDesdeJS`, `abrirModalCerrarTrabajoDesdeJS`, `agendarTrabajoDesdeJS` se declaran en el objeto global `window`.
   * **Corrección:** Encapsular en un namespace Bitrix:
     ```javascript
     BX.namespace('BX.Vitain.PanelPropietario');
     BX.Vitain.PanelPropietario.ActaModal = { ... };
     ```

## 3. Rendimiento y Consultas a HighloadBlocks

### A. Ausencia de Caché Estática en la Compilación ORM
* **Problema Crítico:** En [`RequerimientoHlService.php:1715`](file:///home/bitrix/www/local/components/vita-panel-propietario/panel.propietario/lib/Services/RequerimientoHlService.php#L1715):
  ```php
  private function getHlDataClass(string $hlName)
  {
      $hlblock = HL::getList(['filter' => ['=NAME' => $hlName]])->fetch();
      if (!$hlblock) return null;
      $entity = HL::compileEntity($hlblock);
      return $entity->getDataClass();
  }
  ```
  Cada vez que un método consulta un HighloadBlock, **ejecuta una consulta SQL a `b_hlblock_entity` y recompila dinámicamente la entidad PHP en memoria de ejecución**. En una solicitud compleja donde interactúan 4 HighloadBlocks, se ejecutan entre 6 y 10 queries innecesarias solo de metadatos.
* **Solución Inmediata (Static Memoization):**
  ```php
  private static array $hlClassCache = [];

  private function getHlDataClass(string $hlName): ?string
  {
      if (!isset(self::$hlClassCache[$hlName])) {
          $hlblock = HL::getList(['filter' => ['=NAME' => $hlName]])->fetch();
          if (!$hlblock) {
              return null;
          }
          $entity = HL::compileEntity($hlblock);
          self::$hlClassCache[$hlName] = $entity->getDataClass();
      }
      return self::$hlClassCache[$hlName];
  }
  ```

### B. Indexación de Tablas Físicas de HighloadBlocks (`b_hlbd_*`)
* **Diagnóstico:** Los campos personalizados Bitrix (`UF_*`) en HighloadBlocks se almacenan en tablas planas (`b_hlbd_actas_conformidad`, `b_hlbd_tareas_trabajo`, `b_hlbd_agenda_todistas`).
* **Riesgo:** Por defecto, Bitrix **NO** crea índices B-Tree en la base de datos para los campos `UF_INCIDENCIA_ID`, `UF_TODISTA_ID`, `UF_FECHA_INICIO` o `UF_ESTADO_AGENDA`.
* **Impacto en Producción:** Cuando estas tablas alcancen 20,000+ filas, cada búsqueda de agenda o acta provocará un **Full Table Scan (ALL)** en MySQL, degradando la respuesta del grid a varios segundos.
* **Acción Requerida:** Ejecutar DDL explícito de índices en MySQL:
  ```sql
  ALTER TABLE b_hlbd_agenda_todistas ADD INDEX idx_todista_fechas (UF_TODISTA_ID, UF_FECHA_INICIO, UF_FECHA_FIN);
  ALTER TABLE b_hlbd_tareas_trabajo ADD INDEX idx_incidencia (UF_INCIDENCIA_ID);
  ALTER TABLE b_hlbd_actas_conformidad ADD INDEX idx_incidencia (UF_INCIDENCIA_ID);
  ```

### C. N+1 Query Problem en `UserPermissionService`
* **Código vulnerable en [`UserPermissionService.php:81-127`](file:///home/bitrix/www/local/components/vita-panel-propietario/panel.propietario/lib/Services/UserPermissionService.php#L81-L127):**
  ```php
  $rs = \CIBlockElement::GetList(...);
  while ($el = $rs->GetNext()) {
      $userId = (int)$el['PROPERTY_USER_PROPIETARIO_VALUE'];
      $user = \CUser::GetByID($userId)->Fetch(); // <- ¡1 query por cada fila en el loop!
  }
  ```
* **Solución:** Recolectar todos los `$userIds` y consultar en una única llamada con `\Bitrix\Main\UserTable::getList(['filter' => ['@ID' => $userIds]])`.

## 4. Seguridad, Permisos y Validación (Hallazgos Críticos)

### 🚨 Hallazgo 1: Desactivación Total de Prefilters en `configureActions`
* **Código en [`class.php:86-105`](file:///home/bitrix/www/local/components/vita-panel-propietario/panel.propietario/class.php#L86-L105):**
  ```php
  public function configureActions(): array
  {
      return [
          'validarIncidencia' => ['prefilters' => []],
          'guardarAgendaTrabajo' => ['prefilters' => []],
          'cerrarTrabajo' => ['prefilters' => []],
          'guardarActaConformidad' => ['prefilters' => []],
          // ...todas con prefilters vacíos
      ];
  }
  ```
* **Vulnerabilidad Crítica:**
  * Al colocar `'prefilters' => []`, **se eliminan el `CsrfFilter` (protección contra falsificación de peticiones en sitios cruzados) y el `AuthenticationFilter` (verificación de sesión activa)**.
  * Si un usuario no autenticado o una página externa hace un POST a `/bitrix/services/main/ajax.php?action=vita-panel-propietario.panel.propietario.guardarActaConformidad`, el método lo procesa.
* **Corrección Obligatoria para Producción:**
  ```php
  use Bitrix\Main\Engine\ActionFilter;

  public function configureActions(): array
  {
      return [
          'guardarActaConformidad' => [
              'prefilters' => [
                  new ActionFilter\Authentication(),
                  new ActionFilter\Csrf(),
                  new ActionFilter\HttpMethod([ActionFilter\HttpMethod::METHOD_POST]),
              ]
          ],
          // ...
      ];
  }
  ```

### 🚨 Hallazgo 2: Verificación de SSL Desactivada en `SpringApiClient`
* **Código en [`SpringApiClient.php:164-165`](file:///home/bitrix/www/local/components/vita-panel-propietario/panel.propietario/lib/Repositories/SpringApiClient.php#L164-L165):**
  ```php
  curl_setopt($ch, CURLOPT_SSL_VERIFYPEER, false);
  curl_setopt($ch, CURLOPT_SSL_VERIFYHOST, false);
  ```
* **Riesgo:** Permite ataques de intermediario (Man-in-the-Middle - MITM). En entornos de producción con HTTPS, debe configurarse con certificados válidos y verificación en `true`.

### ⚠️ Hallazgo 3: Autorización Basada en Roles no Homogénea
* En `UserPermissionService` existe lógica para validar si un usuario es `APROBADOR` o residente. Sin embargo, en acciones críticas como `actualizarStockAlmacen` o `cerrarTrabajoAction`, no se valida si el usuario logueado tiene el permiso de rol correspondiente antes de ejecutar la mutación.

## 5. Transacciones y Consistencia de Datos

### Diagnóstico: Inconsistencias Potenciales por Fallos Parciales
Las operaciones de negocio en el componente son **orquestaciones multi-entidad**. Por ejemplo, al ejecutar `cerrarTrabajoAction`:
1. Sube archivos físicos a `b_file` con `\CFile::SaveFile`.
2. Actualiza la tarea en Bitrix24 a estado COMPLETADA (`\Bitrix\Tasks\Item\Task`).
3. Actualiza el registro en `HlTareasTrabajo`.
4. Actualiza el bloque de horario en `HlAgendaTodistas`.
5. Actualiza la cabecera en `HlRequerimientosIncidencia`.
6. Envía un PATCH a la API externa de Spring Boot.

**¿Qué ocurre si el paso 4 o 5 falla por un error de base de datos?**
* **Estado Actual:** Los pasos 1, 2 y 3 quedan confirmados (`AUTOCOMMIT`), mientras que 4 y 5 quedan desfasados. La tarea de Bitrix24 queda cerrada pero el requerimiento queda en estado inconsistente.

### Solución Senior: Implementación de Transacciones D7
```php
use Bitrix\Main\Application;

$connection = Application::getConnection();
$connection->startTransaction();

try {
    // 1. Guardar en HighloadBlock Tareas
    // 2. Guardar en HighloadBlock Agenda
    // 3. Guardar en HighloadBlock Cabecera
    
    $connection->commitTransaction();
} catch (\Throwable $e) {
    $connection->rollbackTransaction();
    // Registrar log estructurado
    throw $e;
}
```

## 6. Idempotencia y Concurrencia

### A. Condición de Carrera en Disponibilidad de Todistas (TOCTOU)
* En `verificarDisponibilidadTodista`:
  1. Se verifica si el todista tiene cruce de horario con `getList()`.
  2. Si está libre, el usuario procede a confirmar en el modal.
  3. En `guardarAgendaTrabajo`, se inserta la reserva.
* **Riesgo de Concurrencia:** Entre el momento en que se verifica y el momento en que se confirma (pueden pasar minutos mientras el usuario llena el formulario), otro coordinador puede asignar al mismo todista en ese mismo horario.
* **Solución Senior:**
  * Validar la disponibilidad de nuevo de forma atómica dentro de la transacción justo antes del `add()`.
  * Implementar bloqueo pesimista mediante `GET_LOCK()` en MySQL o bloqueo a nivel de fila (`SELECT ... FOR UPDATE`).

### B. Idempotencia en Acciones de Formulario
* Para prevenir duplicidad por doble clic del usuario o reintentos de red:
  * Los botones en `costos.js` implementan correctamente la clase `ui-btn-wait` y deshabilitan el click.
  * Se implementó lógica de **Upsert** (actualizar si ya existe por `UF_INCIDENCIA_ID`), lo cual es una **excelente práctica** que previene duplicados en `HlActasConformidad` y `HlTareasTrabajo`.

## 8. Escalabilidad con Grandes Volúmenes de Registros

### Cuello de Botella: Consumo Masivo de API en Memoria
* **Problema:** En [`SpringApiClient.php:26-118`](file:///home/bitrix/www/local/components/vita-panel-propietario/panel.propietario/lib/Repositories/SpringApiClient.php#L26-L118):
  * El método `fetchData()` consulta la URL base del microservicio y descarga **la totalidad de las incidencias existentes** en un solo payload JSON.
  * Posteriormente, en PHP se recorre todo el array en memoria para mapear campos y el filtrado se hace en el servidor local.
* **Impacto en Producción:**
  * Si la inmobiliaria cuenta con 5,000 o 50,000 atenciones históricas, la descarga de megabytes de JSON consumirá la memoria PHP (`Allowed memory size exhausted`) y la solicitud tardará varios segundos.
* **Solución Senior:**
  * Implementar paginación server-side con la API de Spring Boot (`page`, `size`, `sort`, `filter`).
  * Hacer que el Grid de Bitrix solicite únicamente la página activa (`page = 1, limit = 20`).

## 9. Migración de IBlock → HighloadBlock

### Estado de la Migración:
* **Entidades Migradas con Éxito a HighloadBlocks:**
  1. `HlRequerimientosIncidencia` (Cabecera)
  2. `HlRequerimientosItems` (Materiales y Recursos)
  3. `HlPresupuestosIncidencia` (Costos y Presupuestos)
  4. `HlResolucionesAprobacion` (Aprobaciones)
  5. `HlHistorialPlanTrabajo` (Histórico de Fechas)
  6. `HlTodistas` (Personal Técnico)
  7. `HlTareasTrabajo` (Tareas Técnicas)
  8. `HlAgendaTodistas` (Horarios y Calendario)
  9. `HlActasConformidad` (Actas de Entrega y Cierre)

### Entidad Pendiente: IBlock 162 (`Usuarios Propietarios y Aprobadores`)
* Actualmente `UserPermissionService` sigue leyendo de la tabla `b_iblock_element` y `b_iblock_element_property`.
* **Propuesta de Migración:** Crear el HighloadBlock `HlUsuariosRoles` con los campos:
  * `UF_USER_ID` (Integer, ID de usuario Bitrix)
  * `UF_CORREO` (String)
  * `UF_ROL` (Enumeración: APROBADOR, SUPERVISOR, TECNICO, RESIDENTE)
  * `UF_ACTIVO` (Boolean)
* **Beneficio:** Unificación del modelo de datos 100% en D7 HighloadBlocks, eliminando joins pesados de tablas EAV de IBlock.

## 10. Hoja de Ruta y Mejoras Implementadas (Senior Hardening)

### ✅ Mejoras Inmediatas Implementadas y Verificadas en Esta Sesión:
1. **Hardening de Seguridad en Endpoints AJAX (`class.php`):**
   * Se configuraron prefiltros estrictos con `\Bitrix\Main\Engine\ActionFilter\Authentication` y `\Bitrix\Main\Engine\ActionFilter\HttpMethod([POST])` para todas las mutaciones (`guardarActaConformidad`, `cerrarTrabajo`, `guardarAgendaTrabajo`, `actualizarStockAlmacen`, etc.).
   * Se protegieron las acciones de lectura con autenticación mandatoria.
2. **Caché Estática de Clases ORM HighloadBlock (`RequerimientoHlService.php`):**
   * Se implementó **Static Memoization** (`$hlClassCache`) en `getHlDataClass()`. Se eliminaron las consultas redundantes a `b_hlblock_entity` y la recompilación en tiempo de ejecución.
3. **Eliminación del Antipatrón N+1 Queries (`UserPermissionService.php`):**
   * Se refactorizó `getUsuariosPorRolFromIblock162()` para recolectar todos los `$userIds` y consultar en una única llamada batch a `\Bitrix\Main\UserTable::getList()`.
4. **Indexación Física en MySQL de Tablas HighloadBlocks:**
   * Se crearon 8 índices B-Tree en la base de datos MySQL:
     * `b_hlbd_agenda_todistas`: `idx_todista_fechas (UF_TODISTA_ID, UF_FECHA_INICIO, UF_FECHA_FIN)`, `idx_incidencia (UF_INCIDENCIA_ID)`.
     * `b_hlbd_tareas_trabajo`: `idx_incidencia (UF_INCIDENCIA_ID)`, `idx_todista (UF_TODISTA_ID)`, `idx_task (UF_BITRIX_TASK_ID)`.
     * `b_hlbd_actas_conformidad`: `idx_incidencia (UF_INCIDENCIA_ID)`.
     * `b_hlbd_requerimientos_incidencia`: `idx_incidencia (UF_INCIDENCIA_ID)`.
     * `b_hlbd_requerimientos_items`: `idx_incidencia (UF_INCIDENCIA_ID)`.
5. **Transaccionalidad Atómica D7 (`RequerimientoHlService.php`):**
   * Se envolvieron `cerrarTrabajoTodista()` y `guardarActaConformidad()` en transacciones de base de datos (`$connection->startTransaction()`, `$connection->commitTransaction()`, `$connection->rollbackTransaction()`), garantizando consistencia absoluta ante fallos imprevistos.
